# Application delivery platform API with Crossplane and ECR

## Purpose

Use this walkthrough to see what a new platform capability generated by
Crossplane actually represents. A platform team exposes one small
`ApplicationDelivery` API. Its Composition creates an AWS ECR repository and
the Kubernetes resources that run an application image.

This is an architecture and implementation pattern, not an image build system.
Crossplane creates and reconciles the repository and Kubernetes objects. A CI/CD
pipeline builds, signs, scans, and pushes the image. The workload deploys an
image reference only after that artifact exists and is approved.

## Goal and ownership

```text
Platform team                         Application team                    CI/CD system
-------------                         ----------------                    -----------
Installs provider and Function        Creates ApplicationDelivery XR      Builds and pushes image
Owns XRD and Composition               Chooses approved image and scale   Signs/scans/promotes artifact
Owns ECR guardrails                    Reads XR readiness                  Does not edit Composition
```

| Layer | Resource | Responsibility |
| --- | --- | --- |
| API contract | `CompositeResourceDefinition` | Defines the fields application teams may request. |
| Consumer request | `ApplicationDelivery` XR | States application name, image reference, and replicas. |
| Platform implementation | `Composition` | Generates a repository, Deployment, and Service. |
| AWS integration | ECR `Repository` MR | Reconciles the external repository. |
| Kubernetes delivery | `Deployment` and `Service` | Runs and exposes the approved image. |

## Prerequisites

- A supported Kubernetes cluster with Crossplane installed.
- A tested composition Function, such as Patch and Transform.
- An installed and healthy AWS ECR provider plus a least-privilege
  `ProviderConfig` for the target account.
- Namespace RBAC that lets consumers create only the XR, not provider packages,
  Compositions, or privileged ProviderConfigs.
- A CI/CD path that can authenticate to ECR and publish an image before the
  Deployment is expected to become ready.

### Discover the installed ECR API

```bash
kubectl get providers.pkg.crossplane.io
kubectl api-resources | grep -i ecr
kubectl explain repository.ecr.aws.m.upbound.io.spec.forProvider
```

What it does: confirms that the provider is healthy and shows the exact
`Repository` API group and fields available in this cluster. Replace any API
group or field in the examples below if the installed provider exposes a
different schema.

> [!IMPORTANT]
> Pin Crossplane, Function, and provider package versions in Git after testing
> them together. The Upbound marketplace identifies currently available ECR
> provider packages, but a running cluster's CRDs are the authority for a
> manifest.

## Define the consumer API

The XRD intentionally exposes a small request surface. The platform keeps ECR
mutability, scanning, lifecycle, Kubernetes labels, resource defaults, and
network policy decisions out of the consumer contract unless teams have a real
reason to control them.

```yaml
apiVersion: apiextensions.crossplane.io/v2
kind: CompositeResourceDefinition
metadata:
  name: applicationdeliveries.platform.example.com
spec:
  scope: Namespaced
  group: platform.example.com
  names:
    kind: ApplicationDelivery
    plural: applicationdeliveries
  versions:
    - name: v1alpha1
      served: true
      referenceable: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                repositoryName:
                  type: string
                  minLength: 2
                image:
                  type: string
                replicas:
                  type: integer
                  minimum: 1
                  maximum: 10
                  default: 2
              required:
                - repositoryName
                - image
```

What it does: creates the namespaced `ApplicationDelivery` API. It accepts an
image reference because Crossplane does not build or push images. In production,
add admission controls or CI checks that require the image to come from the
approved ECR registry and meet the organization’s signing and scan policy.

## Implement the feature with a Composition

Install a compatible Patch and Transform Function first. Use a reviewed package
reference instead of a floating version.

```yaml
apiVersion: pkg.crossplane.io/v1
kind: Function
metadata:
  name: function-patch-and-transform
spec:
  package: xpkg.crossplane.io/crossplane-contrib/function-patch-and-transform:<reviewed-version-or-digest>
```

What it does: installs the function used by the Composition pipeline. The
function creates the desired set of composed resources; providers reconcile
external resources among that set.

The following Composition is a focused pattern. Validate the ECR resource
fields against the installed provider and add your organization’s resource
requests, security contexts, NetworkPolicies, image policy, tags, and ECR
lifecycle policy before treating it as production-ready.

```yaml
apiVersion: apiextensions.crossplane.io/v1
kind: Composition
metadata:
  name: application-delivery-aws-ecr
spec:
  compositeTypeRef:
    apiVersion: platform.example.com/v1alpha1
    kind: ApplicationDelivery
  mode: Pipeline
  pipeline:
    - step: compose-resources
      functionRef:
        name: function-patch-and-transform
      input:
        apiVersion: pt.fn.crossplane.io/v1beta1
        kind: Resources
        resources:
          - name: ecr-repository
            base:
              apiVersion: ecr.aws.m.upbound.io/v1beta1
              kind: Repository
              spec:
                forProvider:
                  region: <aws-region>
                  imageTagMutability: IMMUTABLE
                providerConfigRef:
                  name: application-delivery-aws
            patches:
              - type: FromCompositeFieldPath
                fromFieldPath: spec.repositoryName
                toFieldPath: spec.forProvider.name
          - name: deployment
            base:
              apiVersion: apps/v1
              kind: Deployment
              spec:
                replicas: 1
                selector:
                  matchLabels:
                    app: placeholder
                template:
                  metadata:
                    labels:
                      app: placeholder
                  spec:
                    containers:
                      - name: application
                        image: placeholder
                        ports:
                          - containerPort: 8080
            patches:
              - type: FromCompositeFieldPath
                fromFieldPath: metadata.name
                toFieldPath: metadata.name
              - type: FromCompositeFieldPath
                fromFieldPath: metadata.namespace
                toFieldPath: metadata.namespace
              - type: FromCompositeFieldPath
                fromFieldPath: metadata.name
                toFieldPath: spec.selector.matchLabels.app
              - type: FromCompositeFieldPath
                fromFieldPath: metadata.name
                toFieldPath: spec.template.metadata.labels.app
              - type: FromCompositeFieldPath
                fromFieldPath: spec.image
                toFieldPath: spec.template.spec.containers[0].image
              - type: FromCompositeFieldPath
                fromFieldPath: spec.replicas
                toFieldPath: spec.replicas
          - name: service
            base:
              apiVersion: v1
              kind: Service
              spec:
                selector:
                  app: placeholder
                ports:
                  - name: http
                    port: 80
                    targetPort: 8080
            patches:
              - type: FromCompositeFieldPath
                fromFieldPath: metadata.name
                toFieldPath: metadata.name
              - type: FromCompositeFieldPath
                fromFieldPath: metadata.namespace
                toFieldPath: metadata.namespace
              - type: FromCompositeFieldPath
                fromFieldPath: metadata.name
                toFieldPath: spec.selector.app
```

What it does: uses one XR to generate three composed resources. The ECR
provider manages the external repository; Kubernetes manages the Deployment and
Service. The `imageTagMutability` setting is a policy choice shown for the
pattern, not a substitute for validating provider support and ECR’s broader
repository controls.

### Why this is a Composition, not a managed resource

The generated `Repository` is a managed resource: it represents one external
AWS ECR repository. `ApplicationDelivery` is a platform API request. The
Composition connects that request to a repository and workload resources. It
can later add a lifecycle-policy MR, a repository-policy MR, image-pull
credentials, a NetworkPolicy, observability, or connection details without
forcing every consumer to learn each provider API.

## Request the feature

```yaml
apiVersion: platform.example.com/v1alpha1
kind: ApplicationDelivery
metadata:
  name: payments-api
  namespace: payments
spec:
  repositoryName: payments-api
  image: <account-id>.dkr.ecr.<aws-region>.amazonaws.com/payments-api:<immutable-tag-or-digest>
  replicas: 2
```

What it does: requests the platform feature. The image must already exist in
ECR and be readable by the target Kubernetes nodes or workload identity. A
digest is the stronger deployment reference when the release process requires
immutable artifact selection.

### Render and validate before applying

```bash
crossplane composition render \
  application-delivery-xr.yaml \
  application-delivery-composition.yaml \
  functions.yaml

kubectl apply --dry-run=server -f application-delivery-xrd.yaml
kubectl apply --dry-run=server -f application-delivery-composition.yaml
```

What it does: renders the expected composed resources locally, then validates
the XRD and Composition against the Kubernetes API without persisting them.
Render output is a review aid, not proof that AWS credentials, IAM permissions,
ECR policy, or the image itself are valid.

### Observe the outcome

```bash
kubectl get applicationdeliveries.platform.example.com -n payments
kubectl describe applicationdelivery payments-api -n payments
kubectl get repository.ecr.aws.m.upbound.io -n payments
kubectl get deployment,service -n payments
```

What it does: checks the request, generated ECR repository, and workload
objects. Inspect XR conditions and events first; then inspect the provider pod
and AWS ECR if the repository does not become ready.

## Operational boundaries and failure modes

| Symptom | Likely boundary or cause | First check |
| --- | --- | --- |
| Repository MR is not ready | Provider package, ProviderConfig, IAM, or ECR API failure. | MR conditions, events, and ECR provider logs. |
| Deployment cannot pull the image | The image was not pushed, reference is wrong, or workload lacks ECR pull access. | Pod events and ECR image details. |
| XR is ready but the app is not | Crossplane created Kubernetes resources, but workload runtime health is separate. | Deployment status, Pods, and application probes. |
| A Composition update changes live resources | XRs follow a new CompositionRevision automatically. | Revision policy and staged render/reconciliation test. |
| A user picks another account’s image | The contract permits an uncontrolled image string. | Admission policy and CI validation of approved registries/digests. |

> [!WARNING]
> Deleting the XR may delete its composed resources and the ECR repository when
> the provider lifecycle policy permits deletion. Empty or retain images and
> other repository dependencies according to the provider and AWS behavior
> before deleting production requests. Never remove Crossplane finalizers merely
> to make deletion finish; first decide whether orphaning the external resource
> is acceptable.

## Production extensions

- Add an ECR lifecycle-policy resource and preview its effect before rollout.
- Use repository and IAM policies to grant only required pull or push access.
- Prefer immutable tags and deploy by digest where release policy requires it.
- Add image signature, vulnerability, and provenance verification in CI/CD or
  admission controls; repository creation alone cannot establish artifact trust.
- Publish the XRD, Composition, Function, and provider dependency as a
  Configuration package once the API contract is stable.
- Promote Composition revisions through development and staging control planes
  before the production API follows them.
